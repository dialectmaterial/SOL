**Companion documents:** [SPECULATIVE](SPECULATIVE.md) (leading) · [BEING](BEING.md) · [ESSENCE](ESSENCE.md) · [CORE](CORE.md).  
**Original adoption:** 17 October 2026 at `main` `1d200e4`; ESSENCE interface and component decisions 18 October 2026 (supporting research: [ESSENCE interface brief](coordination/proposals/ESSENCE_INTERFACE_BRIEF_2026-10-18.pdf)).

> **Interpretation rule.** A statement marked **Implemented** describes inspected code. A statement marked **Decision** expresses the present design direction; it may require code changes. **Proposed** features are not available merely because they appear here. ## 1. What SOL is for

SOL (*SOL Organizes Logic*) is **both a computational investigation into philosophy and a philosophical investigation into computation** ([SPECULATIVE §§1–2](SPECULATIVE.md#1-executive-statement)). Computational procedures give new ways of investigating philosophical texts and categories; philosophical inquiry interrogates the assumptions, methods and limits of those procedures; each may revise the other. Whether computation can become adequate to the Concept, and to the Idea in Hegel's sense, is an **open object of investigation, not a presupposed result**.

For now SOL is centered **exclusively on Hegel's *Science of Logic***, which is both its object of study and, through its logical determinations, an analogical, determinative and revisable principle for organizing SOL's own software ([SPECULATIVE §3](SPECULATIVE.md#3-the-science-of-logic-as-architectural-principle)). Its immediate goal is not a new operating system, a universal PDF importer or a generic ebook reader. It is one continuous practice:

**Read → question → select/contextualize → investigate → inspect evidence → return to the text → revise an interpretation.**

Reading and computational analysis are distinct operations on a shared, identifiable textual object. Their unity consists in preserved source identity, research context and a reversible path to the text, not in sharing a particular terminal window. The decisive acceptance exercise: read a substantial stretch of Hegel, encounter a linguistic or philosophical question, analyze exactly the relevant text, inspect the result, return to the passage, and continue reading without reconstructing context by hand.

### Criteria of success

**Near-term engineering criteria:**

1. **Actual reading:** SOL is pleasant enough to choose voluntarily for a sustained reading session. Visual comfort is judged by a human, not inferred from passing tests or a screenshot.
2. **Fidelity:** source text, editorial material, mathematical passages, hierarchy and provenance remain distinguishable. Unknowns are visible; uncertainty is not silently repaired.
3. **Continuity:** moving into a computational experiment and back does not lose the passage, selected span, active question or reader state.
4. **Reproducibility:** analyses disclose input projection, exact corpus generation, method, parameters, dependency/model versions and results; the system never calls numeric or vector similarity dialectical necessity.
5. **Restraint:** integrate proven tools before creating bespoke interfaces or algorithms. Changes must demonstrably improve the research practice.
6. **Structural soundness during restructuring:** existing functionality still works; the package resolves; tests and entry points run; the logical structure is understandable; major placements carry traceable textual and technical reasons ([SPECULATIVE §9](SPECULATIVE.md#9-risks-and-criteria-of-success)).

**Longer-term philosophical criteria** ([SPECULATIVE §9](SPECULATIVE.md#9-risks-and-criteria-of-success)): the architecture makes the affirmative content of contradictions intelligible rather than cataloguing design conflicts; the logical distinctions illuminate design choices; conceptual difficulties can cause architectural revision; computational results create questions for interpretation; and SOL can state the limits of its methods rather than assuming philosophical success.

## 2. Logical divisions and component responsibilities

**Decision (maintainer, 21 October 2026; [SPECULATIVE §4](SPECULATIVE.md#4-initial-repository-hierarchy)):** substantive modules are to be organized under the logical divisions **BEING** (Quality · Quantity · Measure) and **ESSENCE** (Essence as Reflection within Itself · Appearance · Actuality), with **CONCEPT** reserved as a top-level division whose internal tree is not developed until active work requires it. **CORE** stays a separate service layer for corpus management and shared state: a **practical boundary**, not a philosophical declaration that it can never be rethought. Ordinary engineering infrastructure (tests, configuration, CI, packaging, documentation, tooling) stays outside the hierarchy for now ([SPECULATIVE §6](SPECULATIVE.md#6-limits-of-the-logical-hierarchy)). **Implemented (stage B, 22 October 2026):** the empty divisions exist as packages: `sol/being/{quality,quantity,measure}`, `sol/essence/{essence_as_reflection_within_itself,appearance,actuality}`, and a reserved `sol/concept`, using SPECULATIVE's names. At stage B no module had been placed in them (stage D now fills them; see the register); the stage A inventories are in `docs/coordination/restructuring/`. The restructuring follows the stages in §6.

| Division | Responsibility | Owns today | Must not own |
|---|---|---|---|
| **BEING** | Reading environment and immediate encounter with texts | Neovim reader and its actions, navigation, search, selection, themes, workspaces and attributed personal work, printed-source views | Canonical truth via UI state, model conclusions, terminal dependencies in CORE |
| **ESSENCE** | Computation, analytic methods, comparison, the Textual analysis interface | Method-specific projections, linguistic and statistical studies, result artifacts linked to source records, the methods encyclopedia | Canonical editing, independent passage identity, automatic reader-authored conclusions; the corpus itself, which it requests from CORE |
| **CONCEPT** | Future integration of SOL's research activities and environment, possibly the Omarchy-to-NixOS trajectory | **Nothing implemented or mandated yet** | Premature NixOS/distribution construction |
| **CORE** | Corpus organization, retrieval, metadata, addressability and shared persistent research state | Corpus loader and contract, canonical records, hierarchy, edition attribution, UUID resolution, reference protocol | GUI/TUI, ML runtimes, emulators; it must not silently absorb ESSENCE's computational responsibilities or become a dumping ground |

Internal placement under Quality, Quantity and Measure, or Reflection, Appearance and Actuality, must be argued from the text, never from superficial word associations ([SPECULATIVE §4.1](SPECULATIVE.md#41-what-belongs-where)). Placements are provisional and asymptotic; revision is part of the method ([SPECULATIVE §3.2](SPECULATIVE.md#32-an-asymptotic-revisable-method)). Scholarly interpretation, including of SOL's own structure, remains contestable and attributable.

**Current packages (Implemented; stage D in progress):** `sol.corpus` and `sol.core` (CORE: contract, conversion, verified snapshots, references, configuration, canonical-file resolution in `sol.core.files`, reference CLI in `sol.core.reference_cli`, source capture/rendering in `sol.core.source`, first-run import in `sol.corpus.onboarding`); `sol.being` (BEING, stage D: the reading session `actions`, `surface`, `render`, `shell`; `source_view`, the detached image/PDF viewers; `quality/` search, structure, typography; `quantity/` navigation; `neovim/`, the Neovim reader; `workspace/`, personal research state; **Decision (maintainer, 22 October 2026):** it stays in BEING and moves to CORE only once ESSENCE actually shares it, see the [placement register](#9-placement-register)); `sol.presentation` (shared terminal escaping, theme data and width defaults outside the logical hierarchy); `sol.reader` (the composition root still to move: CLI dispatch, options, launch, `sol read` printing); `sol.essence.essence_as_reflection_within_itself` (ESSENCE engines); `sol.essence` (lazy public engine facade, CLI, catalogs and Textual interface). Not implemented: independent published distributions, a generic investigation desk, a model registry, a NixOS system, a fully graphical typeset reader.

**Decision (maintainer, 18 October 2026): independent components without premature packaging.** BEING reads, ESSENCE investigates, CORE provides verified text; each should become usable without the others where that makes sense, but SOL stays **one installable package** until the seams are proven. The path: (1) **now:** one repository; extract pure-text analysis functions whose tests need neither CORE nor a running interface; (2) **next:** ESSENCE's CLI and interface open ordinary text files, CORE becoming an adapter that adds UUID-backed corpus operations (*implemented for the three studies*); (3) **later:** BEING opens ordinary Markdown without a prebuilt corpus; audit dependencies before proposing separate distributions; (4) **only after stable seams:** separately installable packages, if the maintenance cost is justified. Do not describe SOL as "independently installable" before step 4.

### Dependency direction

CORE provides verified snapshots and references; reader actions mediate reading; terminal adapters adapt to a host; workspaces persist attributed work; ESSENCE uses CORE as an optional provider (studies accept ordinary text files without it). ESSENCE specifies the intended analysis and scope; CORE resolves and provides the material, preserving the distinction between **data organization** and **computational investigation** ([SPECULATIVE §4.1](SPECULATIVE.md#41-what-belongs-where)). CORE must be importable without starting a reader, shell, interactive prompt, workspace, model download or network request. Views do not invent IDs. ESSENCE does not import BEING's interface to obtain data. Reader adapters call the same actions rather than creating parallel navigation semantics. Shared research state survives transitions between BEING and ESSENCE without either interface owning the corpus.

## 3. One book, not every PDF

**Decision, 17 October:** narrow active development to the existing audited Cambridge/George di Giovanni *Science of Logic* corpus. Do not start an arbitrary-PDF importer, multi-book catalog or translation alignment project. Maintain the existing edition/source metadata and make no shortcuts that would obstruct later versions; design further ingestion only when the reader-and-inquiry loop justifies it.

**Direction (SPECULATIVE §4.2):** corpus scopes should become hierarchical and composable: a selection, section, book, an author's body of work, collections and bibliographies as analysis targets or reference corpora. This is a stated intention for CORE's future design ([CORE §1](CORE.md#1-why-core-exists)), not a reason to build a general importer now.

**Implemented:** first interactive `sol` imports the *exact audited source PDF*; it rejects unknown editions, scans and recoded copies. OpenDataLoader produces extraction/review candidates but does not make SOL a general importer. Canonical Markdown is the correction surface; JSONL is generated. Source PDFs, private corpora, crops and analysis exports are never committed. See [CORE](CORE.md).

## 4. User experience: one system, multiple surfaces

`sol` (the same as `sol being`) enters the **isolated Neovim reader** in an ordinary capable terminal; `sol-window` opens it in its own window in a book face. The reader has continuous and one-paragraph reading, search, a structure tree, markers, named places, notes, printed-source views and workspace persistence. Neovim is chosen for its native motion, keymaps, API and maintainability, not because code editing is philosophically the correct way to read a book.

**Decision (maintainer, 18 October 2026): hybrid surfaces for reading and investigation** (confirmed in [SPECULATIVE §4.2](SPECULATIVE.md#42-technical-implications-already-established)). Neovim stays the persistent BEING reader. ESSENCE is a separate **Textual** application started only when requested, inside a Neovim terminal buffer, beside the reader or fullscreen; leaving ESSENCE saves the investigation and ends the process. **Neovim owns the outer layout; Textual owns the layout inside its buffer.** The BEING–ESSENCE contract is semantic; Textual is a presentation of it, not a terminal emulator. Details: [ESSENCE §4](ESSENCE.md#4-interaction-model-and-inquiry-contract), [BEING §6](BEING.md#6-being--essence-without-terminal-dogma). The reverse arrangement (Textual hosting both, Neovim embedded) is an **open alternative** with a proposed test in ESSENCE §4.

**Decision (maintainer, 21 October 2026): a smaller SOL.** `sol-kitty`, the Kitty/Zsh handoff, `sol compare`, the shell's workspace commands, the legacy PDF reader and the reader experiments are removed; `sol --shell` stays as a minimal browsing interface; `sol being` names the reader (bare `sol` still opens it) and `sol essence` names the analysis commands. (This superseded the 17 October decision that kept `sol-kitty` as an optional host.) Terminal splits, browsers, TUI dashboards, CLI output and the TensorFlow Embedding Projector are interchangeable presentations, not competing knowledge stores.

**Themes and typography:** five presets (Catppuccin Mocha, the default, and Latte; SOL's own Paper and Night from actualspirit.com; Terminal); theme changes are presentation only; do not make a theme fork or a second editor distribution; see [BEING §4](BEING.md#4-theming-and-typography). The terminal's cell grid cannot render every typographic feature; **mathematical passages are a test case**: retain source evidence and show the best verified representation, including the printed page in a PDF viewer. A temporary auxiliary window is compatible with a unified research workflow.

## 5. Scholarly discipline

A paragraph UUID represents a source record; a PDF page is evidence/provenance, not the ontology of a logical determination. The edition's hierarchy records its organization, not an incontestable metaphysical structure. Reader-authored notes, comparisons and relations belong to the workspace; model-derived suggestions are separate evidence and never automatically become claims like *presupposes*, *sublates* or *necessary transition*. Distinguish quotation, editorial note, translator decision, computation, human interpretation and proposed philosophical relation.

**Computation** can transform symbol sequences, parse sentences, calculate lexical statistics or embed passages. A statistical relationship can inform philosophical inquiry; it cannot certify dialectical necessity. Every result must remain inspectable against source and method. Hegel states the limit in the Remark to *The particular concept* (Doctrine of the Concept, Subjectivity): numerical and spatial relations, in which the terms fall apart, are "the last and the worst medium" for grasping the concept, which only spirit grasps as concept. SOL's counts, vectors and maps are instruments for approaching the argument, never a claim to reproduce the Concept by calculation; nor is arranging code in a logical tree, or a successful algorithm, evidence of adequacy to the Idea ([SPECULATIVE §2.3](SPECULATIVE.md#23-adequacy-to-the-conceptand-the-idea)).

The same discipline applies to SOL's architecture. Its method is **speculative**, not merely dialectical ([SPECULATIVE §2.4](SPECULATIVE.md#24-why-the-architecture-is-speculative-not-merely-dialectical)): when an arrangement proves inadequate, do not stop at naming the contradiction or discard the old module as a mistake; ask what determinate content survives, what relation the conflict discloses, and what arrangement positively integrates those moments without concealing their tension. Such a result is a provisional proposal, not proof that software has realized speculative reason.

## 6. Development order and acceptance gates

### Restructuring (next; [SPECULATIVE §7](SPECULATIVE.md#7-implementation-sequence))

Incremental and behaviour-preserving:

- **A. Baseline and inventory.** A clean snapshot; inventory packages, imports, entry points, tests and the current CORE/BEING/ESSENCE boundaries without pretending the code is conceptually homogeneous.
- **B. Shallow structure.** Establish the BEING and ESSENCE threefold divisions; CONCEPT reserved; CORE and infrastructure separate.
- **C. Interpretive mapping.** Read the relevant logical sections before proposing placements (§7); group closely related definitions into coherent modules; record references, rationale, alternatives and unresolved cases in the [placement register](#9-placement-register).
- **D. Gradual relocation.** Move modules in small, testable groups; update imports and entry points; protect the reader, corpus access and analytic workflows. No wholesale rewrites in place of a reorganization.
- **E. Re-evaluation.** Review ambiguities and mismatches; add further subdivisions only where the work produces a concrete need and a defensible interpretation.
- **F. Continued reciprocal research.** Let computational results interrogate philosophical assumptions and philosophical analysis question computational techniques; develop CONCEPT only when it becomes a concrete requirement.

Risks to watch ([SPECULATIVE §9](SPECULATIVE.md#9-risks-and-criteria-of-success)): keyword-based classification; triadic symmetry without an established transition; justifications written after the fact; unnecessary churn; CORE as a dumping ground; treating a working algorithm as proof of adequacy to the Idea.

### Product workstreams (continuing, bounded)

**A. Reader quality.** Improve spacing, flow and semantics in the Neovim reader, evaluate the presets, and conduct sustained reading trials; a screenshot or headless test is necessary but insufficient. *Status:* footnote text and in-place numbers, search marks, complete search, page jumps, landmarks, keymaps, the off-screen visual audit and the maintainer's choices (66-column measure, bare focus mode) are implemented; sustained reading trials remain open. Backlog: [reader gaps after Zathura](coordination/proposals/READER_GAPS_AFTER_ZATHURA.md).

**B. Formula fidelity.** Preserve warnings and provenance; previews come from the fingerprint-checked PDF. *Status:* `s` (crop) and `S` (the page in Zathura, highlighted, following the reader) are implemented; 30 scrambled mathematical records were retyped from the crops as linear Unicode and keep `needs_visual_review` until a person confirms each. Reviewed LaTeX/MathML rendering remains future work; the reader must never flatten an unverified formula into apparently certain prose.

**C. First complete inquiry.** From a passage, launch a study in ESSENCE, produce a versioned source-bound artifact, inspect it and return to the source without losing the prior location. *Status:* implemented for word frequencies, sentence lengths and TF-IDF (`E`, Enter on a result, Alt-Left back). Syntactic (POS/dependency) annotation and a human-checked segmentation sample remain open.

**D. ESSENCE interface, then breadth.** Interface shell, word frequencies, comparison and the encyclopedia (with its genealogy) are implemented; model adapters (stage 5, including embeddings for the Embedding Projector) are **deferred by the maintainer** until the interface has improved further. A stage-5 proposal is kept as an open PR for reference.

**E. Later.** Richer annotation spans, research-context restoration, a typeset-reader decision, persistent investigations, additional NLP methods, multilingual and edition handling, CONCEPT, and eventually reproducible Nix-based environment composition. No operating-system distribution in this cycle.

Acceptance includes normal-terminal trials, failure cases, corpus freshness, resizes, Unicode, math preview, a complete research round trip, source return and workspace integrity. Report automated results, integration behaviour, manual visual assessment and known limits **separately**.

### Reader measurements

[`scripts/reader_timings.py`](../scripts/reader_timings.py) is an opt-in developer diagnostic, not an installed command. It defaults to invented text; a private corpus must be selected explicitly:

```sh
.venv/bin/python -B scripts/reader_timings.py --repeats 5 --warmups 1
.venv/bin/python -B scripts/reader_timings.py --corpus /absolute/path/to/local-corpus --json
```

It reports `time.perf_counter` medians, min–max, quartiles and raw samples for load/verification, ordinary and note-heavy payloads, standalone typography, startup to first payload, and controller moves (next/previous, occurrence steps, section boundaries, outline, search/open, history). The controller is real; only its Neovim boundary is replaced; workspaces and state are temporary; generation checks stay enabled. Warm-process figures exclude imports, Neovim launch, IPC, drawing and key-to-screen latency. Stages overlap, so their timings must not be added; and differently sized ordinary and note-heavy sections are not a controlled estimate of footnote overhead. Keep real-book reports outside Git; handoffs may quote them, and optimisations are never adopted from timing differences alone. A proposal to verify corpus fingerprints once per action, with a final check before persistence, is a **reserved** decision awaiting the maintainer.

## 7. Agentic development policy

**Reading obligations ([SPECULATIVE §5](SPECULATIVE.md#5-reading-obligations-for-claude-code-and-codex)).** Agents engage the *Science of Logic* in order to build SOL. Source hierarchy: (1) the edition held in SOL CORE is the **primary working text**; (2) the German original and other translations are permitted aids; (3) secondary commentary is no substitute for the passages. For substantive placements, name the edition and logical location and separate the passage's content from your interpretation. **No fabricated quotations, page numbers or textual evidence.**

**Reasoning protocol** for creating a logical directory, moving a significant module or reorganizing a cohesive cluster: **read** the pertinent part of the primary text and nearby transitions; **interpret** the determination in relation to its neighbours (no keyword matching between code and chapter titles); **inspect** what the code does, depends on and what its tests protect; **propose** a provisional placement and why it beats the alternatives; **implement** without gratuitously rewriting working logic; **verify** with tests, static and entry-point checks; **record and reconsider** in the [placement register](#9-placement-register), keeping in a conflict both the determinate limitation of the old arrangement and the positive content carried into the new. This applies to module-level decisions, not to every helper.

**Autonomy (Decision, [SPECULATIVE §5.3](SPECULATIVE.md#53-autonomy-and-final-authority)):** Claude Code and Codex may make and implement provisional structural decisions without asking for each move, keeping their reasoning traceable and changes reviewable; the maintainer has the final say and may revise any decision. Still **reserved** for the maintainer (see CLAUDE.md): changes to **Decision** statements, public contracts (CORE API, reference protocol, corpus contract, workspace schema), the dependency set, and anything that deletes or overwrites personal work or the canonical corpus.

**Working practice:**

- Start from `git status`, recent commits, these five documents and the relevant code and tests. Never assume a prior handoff is the current state. Do not discard uncommitted work.
- Treat these documents as the authoritative design description. If implementation disagrees, report it; do not pretend a planned feature exists. Update the docs with verified changes.
- History lives in Git: prior reports, hypotheses and failed prototypes are not binding because they were once written.
- Run focused tests, then the full suite. Passing tests are not evidence of good reading, transcription accuracy, attribution or philosophical correctness.
- Work on a dedicated branch in coherent commits; preserve public behaviour where possible. Never commit copyrighted book material, private workspaces, extracted PDF content or user data.
- Prefer incremental changes preserving passage IDs, source digests, existing workspaces and public CORE contracts. Any explicit migration must be reversible or publish a new copy.

## 8. Documentation policy

**Five documents govern SOL:** [SPECULATIVE](SPECULATIVE.md) leads, setting the aim, method, logical organization and agent protocol; this charter, [BEING](BEING.md), [ESSENCE](ESSENCE.md) and [CORE](CORE.md) describe the system in its terms. SPECULATIVE is the maintainer's architectural decision record and is changed only by the maintainer; the others are kept consistent with it. Research briefs and proposals under `docs/coordination/proposals/` are supporting evidence; their decisions apply only as recorded in the five documents. The root `README.md` is a gateway, not a sixth source. Chronological history is CHANGELOG and Git; old documents and finished proposals leave the tree once anything still valid has moved into the five. A code-level invariant belongs in tests and code as well as a concise statement in CORE.
